# i18n

Lyvely offers a flexible solution for managing translations across both the frontend and backend. While the majority of 
translations are handled on the frontend, certain content like notifications and emails must be translated on the backend.

## Frontend Translations

### Registration of Translations

In the frontend translations remain in the `locales` directory of a module and are configured by the `i18n` module
option. This option enables you to register translations, which can either be loaded on demand or on first page load.

The following types of translation files are available:

- `base`: This locale file will be loaded once the application starts and may contain translations that need to be
  available on startup, such as menu entries or notification texts.
- `locale`: This is the default locale file of the module and may be loaded when accessing module-related routes.
- Other translation files, known as sections, can be loaded on demand within a route, guard or view and typically contain 
translations specific to a view or view section.

In the following example we configure our root to load the default `locale` from the `polls` module.

```typescript
export const pollsRoutes: RouteRecordRaw[] = [
  {
    name: 'Polls',
    path: profilePath('/polls'),
    meta: {
      i18n: { load: ['polls'] }, // This will load the the default locale when entering the route.
      layout: LAYOUT_PROFILE,
      title: () => t('polls.title'),
    },
    component: () => import('../views/PollsView.vue'),
  },
];
```
The `locale` file is registered in our module alongside with our `base` translations, which are loaded on startup:

```typescript
export const pollsModule = () => {
  return {
    id: POLLS_MODULE_ID,
    i18n: {
      base: (locale: string) => import(`./locales/base.${locale}.json`),
      locale: (locale: string) => import(`./locales/${locale}.json`),
    },
    routes: pollsRoutes,
    init: () => {
      // Other module initialization logic
    },
  } as IModule;
};
```
You can also load non default translation files within your route definition, even from other modules as follows:

```typescript
export const myRoutes: RouteRecordRaw[] = [
  {
    name: 'MyView',
    path: profilePath('/my-view'),
    meta: {
      // Here we load the login.${locale}.json file of the auth module
      i18n: { load: [{ module: 'auth', section: 'login' }] },
      layout: LAYOUT_PROFILE,
      title: () => t('my-view.title'),
    },
    component: () => import('../views/MyView.vue'),
  },
];
```

### Frontend Text Translation

Lyvely uses [vue-i18n](https://vue-i18n.intlify.dev/) for text translations in the frontend. The `@lyvely/web` package 
also includes a `t` translation function. Most components in the `@lyvely/ui` library expect translation strings for 
displaying text. Below, we provide examples demonstrating various ways to handle text translations in the frontend.

#### The `t` Helper

The `t` helper function can be used anywhere in your frontend as in the following example:

```typescript
import { t } from '@lyvely/web';

const translated = t('my-module.some.text', { someParam: 'value' });
```

#### The `<i18n-t>` Component

The [vue-i18n](https://vue-i18n.intlify.dev/) library provides a `<i18n-t>` component, which can be used within your
template files:

```html
<i18n-t keypath="my-module.some.text" tag="p" class="mb-5">
  <template #someParam>
    <b>value</b>
  </template>
</i18n-t>
```

:::tip
Please refer to the [vue-i18n Guide](https://vue-i18n.intlify.dev/guide/installation.html) for more information.
:::

#### Lazy Translation with `translation`

The `translation` helper of the `@lyvely/web` package can be used for use-cases in which you want to assign translations
before they are loaded. This for example is used when defining translatable route titles:

```typescript
export default [
  {
    path: profilePath('/my-module'),
    name: MY_MODULE_ROUTE_NAME,
    meta: {
      title: translation('my-module.title'),
    },
    component: () => import('../views/MyView.vue'),
  },
];
```

#### `@lyvely/ui` Component Translation

The `Translatable` interface of `@lyvely/ui` ist often used for component properties, which support translations by default:

```html
<script type="ts" setup>
import { t, Translatable } from '@lyvely/ui';

const props = defineProps<{
  text: Translatable
}>()
</script>

<template>
  {{ t(text) }}
</template>
```

Most components of the `@lyvely/ui` library expect translation strings for labels and other texts. So you can conveniently
use translation texts as follows:

```html
<ly-button text="my-module.button-text" />
```

You can skip the translation step as follows:

```html
<ly-button :text="{ raw: 'MyButton' }" />
```

## Locale handling in the backend

In the backend our translations files do also remain in the `locales` directory of a module. The `I18n` component can
be used to translate text as in the following example:

```typescript
@Injectable()
export class MyBackendService {
  constructor(private readonly  i18n: I18n) {}
  
  async sendTestEmail(host: User, target: User) {
    const i18n = this.i18n.translation('my-module', target);
    const subject = i18n.t('test-mail.subject', { host: host.getDisplayName() })
    // ...
  }
}
```

In the previous example, we created an `i18n` module translation helper object for the `my-module` translations, 
utilizing the user's locale as the target.

:::note
For this to work our module needs to use the `@LyvelyModule` decorator. Also, make sure your translation files are
copied correctly, when building your module.
:::
